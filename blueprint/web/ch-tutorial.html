1 How Lean thinks: goals, context, term vs. tactic mode

Every Lean proof is, underneath, a term — a value whose type is the proposition being proved. theorem add_comm’ (a b : Nat) : a + b = b + a := Nat.add_comm a b is a complete proof written directly as a term: Nat.add_comm a b is a value, and its type happens to be a + b = b + a.

Writing proof terms directly gets unwieldy fast, so almost all real proofs use tactic mode, entered with by: 

theorem add_comm' (a b : Nat) : a + b = b + a := by
  exact Nat.add_comm a b

Inside by, you’re not writing a term — you’re issuing tactics, each of which transforms a goal state into a new (possibly empty) goal state. A goal state looks like: 

a b : Nat
⊢ a + b = b + a

Above ⊢ is the local context: every variable and hypothesis currently in scope. After ⊢ is the goal: the proposition still to be proved. A tactic either closes the goal (context becomes empty — done), transforms it into a different goal, or splits it into multiple goals (e.g. one per case of an induction).

This is exactly the loop this project automates: an LLM agent looks at a goal state, proposes one tactic, and Lean reports back either a new goal state or an error. Everything in this tutorial is really a catalog of the “moves” the agent has available at each step, which is why the taxonomy of which move it picks — and how often it picks a wrong one — is the statistical object of interest for the hallucination analysis (see docs/resources.md §5).

A style note before we start: Lean tactic mode is whitespace-sensitive in a specific way — tactics separated by newlines run in sequence on the current (first) goal; · (a centered dot, typed \.) explicitly focuses a single goal so that indented tactics under it apply only there. You’ll see this constantly once goals start splitting (§5 onward).

2 Core tactics I — closing goals

2.1 rfl — reflexivity

Closes a goal a = a up to Lean’s notion of definitional equality — not just syntactic identity, but anything that reduces to the same normal form by unfolding definitions and computing. 

example : 2 + 2 = 4 := by rfl
example (n : Nat) : n = n := by rfl

rfl fails as soon as the two sides aren’t definitionally equal, even if they’re provably equal by some other route — that’s when you need rw, simp, ring, or omega instead.

2.2 exact — direct proof

exact e closes the goal by supplying a term e whose type matches exactly. 

example (h : 2 + 2 = 4) : 2 + 2 = 4 := by exact h
example (n : Nat) : n + 0 = n := by exact Nat.add_zero n

If you don’t know the exact lemma name, exact? searches the library and suggests one: 

example (n : Nat) : n + 0 = n := by exact?
-- Suggests: exact Nat.add_zero n

2.3 apply — working backwards

apply e unifies the conclusion of e’s type with the goal, and turns any remaining premises of e into new goals. Where exact needs everything handed to it, apply lets Lean fill in what it can infer and leaves the rest for you. 

example (a b c : Nat) (hab : a = b) (hbc : b = c) : a = c := by
  apply Eq.trans
  · exact hab
  · exact hbc

Eq.trans : a = b → b = c → a = c doesn’t fully match the goal a = c on its own — apply inserts a metavariable for the missing middle term and creates two new goals for the two premises. This is exactly why apply sometimes produces goals that look stranger than the original: it’s exposing structure the lemma needed that wasn’t visible in your one-line goal.

apply? is the library-search analog for apply.

2.4 assumption

Scans the local context for a hypothesis whose type matches the goal exactly, closing it if found. 

example (P Q : Prop) (hp : P) (hq : Q) : P := by assumption  -- finds hp

2.5 Quick reference

Tactic

Use when

exact e

You have exactly what’s needed

apply lemma

Lemma’s conclusion matches; premises become new goals

assumption

Goal matches a hypothesis, don’t want to name it

rfl

Both sides compute to the same value

exact? / apply?

You don’t know the lemma name

3 Core tactics II — rewriting

3.1 rw — precise, one substitution at a time

Given h : a = b, rw [h] finds a in the goal and replaces every occurrence with b. 

example (a b : Nat) (h : a = b) : a + 1 = b + 1 := by
  rw [h]   -- goal becomes b + 1 = b + 1

Note this closes automatically — rw calls rfl after rewriting if that finishes the goal. Direction matters: rw [h] goes left-to-right (per h’s statement); rw [← h] (type \l or \leftarrow for ←) goes right-to-left. 

example (a b : Nat) (h : a + 1 = b) : b = a + 1 := by
  rw [← h]   -- replaces b with (a + 1); goal becomes a + 1 = a + 1

Chain multiple rewrites in one call — they apply left to right in sequence: 

example (a b c : Nat) (h1 : a = b) (h2 : b = c) : a = c := by
  rw [h1, h2]

Rewrite inside a hypothesis instead of the goal with at: 

example (a b : Nat) (h1 : a = b) (h2 : a + 1 = 5) : b + 1 = 5 := by
  rw [h1] at h2
  exact h2

Common trap: rw replaces all syntactic occurrences of the LHS pattern, which is occasionally more than you want (rw [h] on a + a = 10 with h : a = b gives b + b = 10, not just one side). Use nth_rewrite n [h] to target a specific occurrence.

3.2 simp — automated simplification

Where rw applies rules you name, simp repeatedly applies a large database of lemmas tagged @[simp] until nothing more simplifies, and frequently closes the goal outright. 

example (n : Nat) : n + 0 + 0 + 0 = n := by simp
example (xs : List Nat) : xs ++ [] = xs := by simp

Feed it extra lemmas or local hypotheses in brackets: 

example (a b : Nat) (h : a = 5) : a + b = 5 + b := by simp [h]

simp is not omniscient. It’s a simplifier, not a general prover — it won’t discover a proof strategy, only apply known-good rewrite rules to a fixed point. a * (b + c) = a*b + a*c is not closed by bare simp (distributivity isn’t tagged @[simp]); that’s a job for ring.

Four variants worth knowing cold:

Variant

Behavior

simp only [l1, l2, ...]

Uses only the listed lemmas — reproducible, doesn’t silently change behavior if the global simp set grows. Preferred in anything meant to be stable.

simp_all

Simplifies the goal and every hypothesis, using each hypothesis as an extra rewrite rule. Powerful for messy contexts, but harder to predict.

simp?

Runs simp, then prints the minimal simp only [...] that achieves the same result — the standard way to convert an exploratory simp into a reproducible one.

dsimp

Definitional simplification only — unfolds/computes, never applies a proved rewrite lemma. Never fails unexpectedly, but also never does as much. 

example (n : Nat) : n + 0 = n := by
  simp?
  -- Try this: simp only [Nat.add_zero]

simp at h / simp at * target hypotheses or everything at once, exactly like rw’s at.

3.3 norm_num, norm_cast, push_cast

norm_num proves/simplifies goals about concrete numerals (21 - 6 = 15). norm_cast/push_cast normalize numeric-type coercions (moving between ℕ, ℤ, ℚ, ℝ) — essential once problems mix integer and real arithmetic, common in the topology/analysis parts of the problem set.

4 Core tactics III — introducing and structuring

4.1 intro — assuming hypotheses

When the goal is an implication P → Q or a universal ∀ x, P x, intro moves the antecedent/quantified variable into the context. 

example (P Q : Prop) : P → Q → P := by
  intro hp hq
  exact hp

example : ∀ n : Nat, n = n := by
  intro n
  rfl

intro can destructure as it introduces: 

example (P Q : Prop) : P ∧ Q → Q ∧ P := by
  intro ⟨hp, hq⟩
  exact ⟨hq, hp⟩

Prefer explicit names (intro n hn) over the bare intros, which auto-generates opaque names like a✝ — fine for quick exploration, bad for anything you or an agent needs to refer back to later in the proof.

4.2 have and let — intermediate steps

have h : T := proof states and proves an intermediate fact, adding h : T to the context. The value is opaque afterward — only its type matters to the rest of the proof. 

example (a b : Nat) (ha : a > 5) (hb : b > 3) : a + b > 8 := by
  have hab : a + b > 5 + 3 := by omega
  omega

let x := val introduces a transparent local definition — its value, not just its type, is visible to later tactics like rfl. 

example : 10 = 5 + 5 := by
  let x := 5
  rfl   -- works because x unfolds to 5

Use have for propositions/proofs you’ll reference by type; use let for computed values you want to reuse and potentially unfold later.

4.3 suffices — working backwards from a stronger claim

suffices h : T by tac replaces the goal with T, where tac discharges the original goal assuming h : T. 

example (n : Nat) : n + n ≥ n := by
  suffices h : n ≤ n + n by omega
  omega

Read it as: “it suffices to show T; here’s how T implies what I actually wanted (by tac); now let me prove T.”

4.4 show — restating the goal

show T changes the displayed goal to a definitionally-equal T — purely for clarity/debugging, doesn’t change what’s actually being proved.

5 Case analysis and induction

5.1 cases — splitting on constructors

cases x produces one goal per constructor of x’s type, replacing x with that constructor’s shape in each branch. 

example (b : Bool) : b = true ∨ b = false := by
  cases b with
  | true => left; rfl
  | false => right; rfl

example (n : Nat) : n = 0 ∨ n > 0 := by
  cases n with
  | zero => left; rfl
  | succ m => right; omega

cases also works on propositions built from inductive types — Or has two constructors (inl/inr), And has one with two fields: 

example (P Q R : Prop) (h : P ∨ Q) (hpr : P → R) (hqr : Q → R) : R := by
  cases h with
  | inl hp => exact hpr hp
  | inr hq => exact hqr hq

5.2 induction — proof by mathematical induction

induction x with produces a base case and, for each recursive constructor, a step case that includes an induction hypothesis ih. 

theorem add_zero' (n : Nat) : n + 0 = n := by
  induction n with
  | zero => rfl
  | succ m ih =>
    -- ih : m + 0 = m
    -- goal : (m + 1) + 0 = m + 1
    simp [ih]

The induction hypothesis is the entire point — it’s the license to assume the property holds for the smaller case while proving it for the larger one. Forgetting to use ih (proving the step case “from scratch”) is a common failure mode both for beginners and, notably, for agents that don’t track what’s actually available in context.

5.3 rcases / obtain — recursive destructuring (Mathlib)

cases gets unwieldy once structures nest (an ∃ inside an ∧ inside an ∃…). rcases/obtain (both require import Mathlib.Tactic.Cases / are available under import Mathlib.Tactic) destructure all of that in one pattern. 

example (h : ∃ n m : Nat, n < m ∧ m < 10) : True := by
  rcases h with ⟨n, m, hnm, hm10⟩
  trivial

example (h : ∃ n : Nat, n > 0 ∧ n < 10) : True := by
  obtain ⟨n, hn_pos, hn_lt⟩ := h
  trivial

Pattern language: ⟨p1, p2⟩ destructs pairs/∃/∧; p1 | p2 splits ∨; rfl substitutes an equality the instant it’s introduced (extremely handy — see below); _ discards a part you don’t need. 

example (h : ∃ n : Nat, n = 5) : 5 = 5 := by
  rcases h with ⟨_, rfl⟩   -- n is substituted by 5 everywhere
  rfl

rintro fuses intro with an rcases pattern: rintro ⟨a, b⟩ ⟨c, d⟩ introduces and destructures two arguments in one line.

cases/induction vs. rcases/obtain: the former are core-Lean and exhaustive (they force you to name every constructor case); the latter are Mathlib conveniences layered on top, better for existentials and nested nonsense, worse for anything where you actually need the inductive structure (like a genuine induction).

6 Automation and decision procedures

These tactics are decision procedures or heuristic search over specific fragments of mathematics — when your goal falls in their fragment, they either succeed or definitively fail (no partial credit, no “almost”).

6.1 omega — linear arithmetic over ℕ/ℤ

Handles +, -, comparisons, and multiplication/division/modulo by constants (not variable × variable). 

example (n : Nat) : n ≤ n + 1 := by omega
example (a b c : Nat) (h1 : a ≤ b) (h2 : b < c) : a < c := by omega
example (n : Nat) : n / 2 ≤ n := by omega
example (n : Nat) (h : n % 2 = 0) : 2 * (n / 2) = n := by omega

omega automatically pulls in every relevant hypothesis in context — you never tell it which ones to use. It correctly understands Nat’s truncated subtraction (a - b = 0 when a < b) and Int’s standard subtraction, which is a frequent source of confusion when porting a proof between the two.

It fails immediately on anything nonlinear: 

-- example (x y : Nat) : x * y = y * x := by omega   -- fails: nonlinear
example (x y : Nat) : x * y = y * x := by ring         -- use ring instead

6.2 ring / ring_nf — polynomial identities

Proves equalities that follow purely from ring axioms (associativity, commutativity, distributivity) — no need to spell out the expansion by hand. 

example (x y : Int) : (x + y)^2 = x^2 + 2*x*y + y^2 := by ring
example (a b c : Int) : (a + b + c)^2 = a^2+b^2+c^2 + 2*a*b + 2*b*c + 2*a*c := by ring

ring cannot handle division (use field_simp first) or inequalities (use nlinarith) or anything involving an opaque function. ring_nf normalizes an expression to canonical form without requiring it close the goal — useful mid-proof.

6.3 linarith / nlinarith — linear / mildly-nonlinear inequalities

linarith proves linear (in)equalities from hypotheses over ordered fields, by finding a linear combination that derives a contradiction from the negated goal. nlinarith extends it with limited nonlinear preprocessing (it can use provided facts like squares being nonnegative): 

example (x : Int) : x * x ≥ 0 := by nlinarith [sq_nonneg x]

6.4 decide / native_decide

Evaluate a Decidable proposition directly to true/false. decide runs inside the kernel (slow, fully trusted); native_decide compiles to native code first (fast, relies on trusting the compiler — appropriate for larger finite checks, not for anything safety-critical in the proof).

6.5 aesop — general automated search

aesop searches over a registered rule set (@[aesop]-tagged lemmas plus built-ins) trying to close the goal by whatever combination works. aesop? prints the proof it found, which is the standard way to turn an aesop call into a reproducible, auditable tactic sequence.

7 Structuring proofs

7.1 by_contra — proof by contradiction

by_contra h turns a goal P into a goal False, adding h : ¬P to the context. 

example (P : Prop) (h : ¬P → False) : P := by
  by_contra hP
  exact h hP

7.2 by_cases — splitting on a proposition

by_cases h : P produces two goals: one with h : P, one with h : ¬P. 

example (n : Nat) : n = 0 ∨ n ≠ 0 := by
  by_cases h : n = 0
  · exact Or.inl h
  · exact Or.inr h

Both tactics rely on classical reasoning (excluded middle) — standard throughout Mathlib, but worth knowing if a proof needs to stay constructive.

7.3 contrapose / push_neg

contrapose turns a goal P → Q into ¬Q → ¬P; contrapose! additionally runs push_neg on the result. push_neg on its own pushes a ¬ inward through quantifiers and connectives via De Morgan’s laws — e.g. turning ¬∀ x, P x into ∃ x, ¬P x, or ¬(a < b) into b ≤ a. Both are usually paired with by_contra or by_cases to get a negated hypothesis into a usable shape rather than a raw ¬(...) blob.

7.4 calc — calculational proofs

Chains a sequence of relational steps, each independently justified, reading like a proof on paper. 

example (a b c d : Nat) (h1 : a = b) (h2 : b < c) (h3 : c ≤ d) : a < d := calc
  a = b := h1
  _ < c := h2
  _ ≤ d := h3

Each _ refers to the previous line’s right-hand side. calc can mix relations (=, <, ≤, ≠) as long as they compose transitively, and any tactic can justify a step: 

example (x y : Int) : (x + y)^2 = x^2 + 2*x*y + y^2 := calc
  (x + y)^2 = (x + y) * (x + y) := by ring
  _ = x*x + x*y + y*x + y*y       := by ring
  _ = x^2 + 2*x*y + y^2           := by ring

calc is worth reaching for whenever a proof’s legibility matters as much as its correctness — which, notably, includes anywhere you’d want a human (or a later analysis pass) to audit why the agent believed a step, not just that Lean accepted it.

8 Equality machinery: ext, funext, congr, symm, trans

8.1 funext and ext — extensionality

Two functions are equal exactly when they agree everywhere; two sets are equal exactly when they have the same elements. funext x reduces f = g to f x = g x; ext (Mathlib, more general) applies whatever extensionality lemma fits the goal’s type — functions, sets, structures, products. 

example : (fun x : Nat => x + 0) = (fun x => x) := by
  funext x
  simp

example (A B : Set Nat) (h : ∀ x, x ∈ A ↔ x ∈ B) : A = B := by
  ext x
  exact h x

example (A B : Set α) : A ∩ B = B ∩ A := by
  ext x
  constructor
  · intro ⟨ha, hb⟩; exact ⟨hb, ha⟩
  · intro ⟨hb, ha⟩; exact ⟨ha, hb⟩

Marking a custom structure @[ext] auto-generates an extensionality lemma the ext tactic can then use.

8.2 congr — from function equality to argument equality

congr reduces a goal f a = f b to a = b (and, for multi-argument functions, one subgoal per argument).

8.3 symm / trans

symm flips a = b to b = a in the goal; trans y splits a = c into a = y and y = c — the tactic-mode analog of a manual Eq.trans/one calc step.

9 Tactic combinators

Combinators glue tactics together without you manually tracking every resulting goal: 

-- Runs `simp` on every goal produced by `cases`
example (b : Bool) : b || true = true := by cases b <;> simp

-- Focuses exactly the first goal
example (P Q : Prop) (hp : P) (hq : Q) : P ∧ Q := by
  constructor
  · exact hp
  · exact hq

Combinator

Behavior

t1 <;> t2

Run t2 on every goal t1 produces

· tac

Focus the first goal; tac must close it

first | t1 | t2

Try t1; on failure try t2

repeat tac

Repeat until tac fails

all_goals tac

Run on every goal; fails if any fails

any_goals tac

Run on every goal; fails only if none succeed

These matter for the agent harness specifically: a single agent-proposed “tactic” is often, in practice, a short combinator expression (intro n; cases n <;> simp) rather than one atomic step — which affects how we define “one iteration” in the statistical analysis (see docs/resources.md §5 and the Agent\(\leftrightarrow \)Lean 4 Pipeline chapter).

10 Worked examples — Set theory

Sets in Mathlib are Set α for some ambient type α; membership is x ∈ s. The single most useful tactic here is ext — almost every “these two sets are equal” goal reduces to “these two sets have the same members,” which reduces to an iff you prove pointwise. 

-- Intersection is commutative
example (A B : Set α) : A ∩ B = B ∩ A := by
  ext x
  simp only [Set.mem_inter_iff]
  tauto

-- Distributivity of ∩ over ∪
example (A B C : Set α) : A ∩ (B ∪ C) = (A ∩ B) ∪ (A ∩ C) := by
  ext x
  simp only [Set.mem_inter_iff, Set.mem_union]
  tauto

-- Subset proofs: intro the element, chase membership
example (A B C : Set α) (h1 : A ⊆ B) (h2 : B ⊆ C) : A ⊆ C := by
  intro x hx
  exact h2 (h1 hx)

-- Existentials over sets
example (A : Set Nat) (h : ∃ n ∈ A, n > 5) : ∃ n, n ∈ A := by
  obtain ⟨n, hn, _⟩ := h
  exact ⟨n, hn⟩

Note the pattern: ext x to get down to elements, simp only [Set.mem_...] (or plain simp) to unfold membership into a propositional statement, then propositional tactics (tauto, constructor, intro/exact) to close it. ⊆ unfolds definitionally to ∀ x, x ∈ A → x ∈ B, so subset proofs are almost always intro x hx; ....

11 Worked examples — Topology

Mathlib’s TopologicalSpace α typeclass carries an IsOpen : Set α → Prop predicate plus the usual axioms (arbitrary unions of opens are open, finite intersections of opens are open, the whole space and empty set are open). A function f : α → β between topological spaces is Continuous f exactly when the preimage of every open set is open — this is the recurring proof shape for continuity goals. 

-- Continuity as preimage-of-open-is-open (schematic — exact lemma names
-- depend on the specific Mathlib continuity API in scope; verify with #check
-- or `exact?` before relying on this in a real proof)
example {α β : Type*} [TopologicalSpace α] [TopologicalSpace β]
    (f : α → β) (h : ∀ U, IsOpen U → IsOpen (f ⁻¹' U)) : Continuous f := by
  exact continuous_def.mpr h

Limits are expressed via Tendsto and neighborhood filters 𝓝: “the limit of 2*x as x → 3 is 6” is Tendsto (fun x : ℝ => 2 * x) (𝓝 3) (𝓝 6). Continuity-at-a-point is definitionally ContinuousAt f x ↔ Tendsto f (𝓝 x) (𝓝 (f x)). 

-- A continuous function composed with a continuous function is continuous
example {α β γ : Type*} [TopologicalSpace α] [TopologicalSpace β] [TopologicalSpace γ]
    (f : α → β) (g : β → γ) (hf : Continuous f) (hg : Continuous g) :
    Continuous (g ∘ f) := by
  exact hg.comp hf

Honest caveat for this section: topology proofs lean heavily on knowing the right Mathlib lemma name (Continuous.comp, continuous_def, IsOpen.inter, etc.) rather than on generic tactics — this is precisely the regime where exact?/apply?/#loogle stop being optional conveniences and become load-bearing. Expect this to be a rich source of “wrong lemma name” hallucinations once the agent starts working topology problems — worth flagging explicitly in the error taxonomy (docs/resources.md §5, and the future logging-system doc).

12 Worked examples — Algebra

Mathlib’s algebraic hierarchy (Monoid, Group, Ring, Field, …) is built from typeclasses; a Subgroup G is a bundled structure (carrier set + closure proofs), and a group homomorphism f : G →* H is a bundled function plus a proof it respects multiplication (map_mul). 

-- Basic group identities, provable purely from the group axioms
example {G : Type*} [Group G] (a b : G) : (a * b)⁻¹ = b⁻¹ * a⁻¹ := by
  exact mul_inv_rev a b

example {G : Type*} [Group G] (a : G) : a * a⁻¹ = 1 := by
  exact mul_inv_cancel a

-- Homomorphisms preserve the identity and inverses
example {G H : Type*} [Group G] [Group H] (f : G →* H) (a : G) :
    f (a⁻¹) = (f a)⁻¹ := by
  exact map_inv f a

-- Subgroup membership is closed under the group operation
example {G : Type*} [Group G] (H : Subgroup G) (a b : G) (ha : a ∈ H) (hb : b ∈ H) :
    a * b ∈ H := by
  exact H.mul_mem ha hb

For concrete numeric rings (ℤ, ℚ, ℝ, polynomial rings), reach for ring/ring_nf first — it closes anything that follows from ring axioms alone without needing a single named lemma: 

example (a b : Int) : (a + b) * (a - b) = a^2 - b^2 := by ring

Recurring pattern across all three topic areas: generic tactics (ring, omega, simp, tauto, ext) get you very far in set theory and basic algebra, where the underlying structure is “compute and compare.” Topology (and deeper algebra — quotients, isomorphism theorems) leans much more on finding the specific lemma that encodes the mathematical fact you need, which is a fundamentally different skill — and, again, plausibly a different hallucination profile for the agent to exhibit. This distinction should directly inform how the problem set (docs/resources.md, Goal 9) is difficulty-tiered.

13 Reading errors and diagnosing failed proofs

Lean’s error messages are the raw signal the agent harness will parse programmatically (see the pipeline chapter), so it’s worth learning to read them precisely rather than pattern-matching on vibes.

“type mismatch” — the term you supplied has a different type than the goal expects. Almost always from exact, or an apply where unification failed silently upstream. Read the expected vs. got types Lean prints; the mismatch is usually one argument, one implicit, or a coercion away.

“unknown identifier / unknown constant” — you referenced a lemma name that doesn’t exist (wrong name, wrong namespace, or it’s simply not the name Mathlib uses). This is the single most common hallucination failure mode for an LLM proposing tactics: confidently citing a plausible-sounding lemma (Nat.mul_comm_left when the real name is Nat.mul_left_comm, say) that was never in the library. exact?/apply?/#loogle exist specifically to route around needing to remember exact names.

“failed to synthesize instance” — a typeclass Lean needs (e.g. TopologicalSpace α, DecidableEq α) isn’t available in context. Usually means a hypothesis or variable declaration is missing, not that the proof strategy is wrong.

“unsolved goals” at the end of a by block — the tactic sequence ran out without closing everything. Check the last-printed goal state; it tells you exactly what’s left.

A goal that doesn’t shrink after a tactic that “succeeded” (no error, but the goal looks identical) — almost always rw/simp finding nothing to rewrite, silently doing nothing rather than erroring. Worth explicitly distinguishing from a genuine error in the agent’s logs: tactic accepted but made no progress is a distinct category from tactic rejected, and both are distinct again from tactic accepted, goal changed, but agent is now further from a proof than before.

sorry compiles. A file with sorry anywhere in a proof still type-checks and reports no errors — Lean treats sorry as “trust me.” This is the sharpest trap for automated pipelines: a proof search that terminates because the agent inserted sorry looks, from the outside, identical to success unless you explicitly grep for it. Any harness built on top of this tutorial’s material must treat sorry/admit as a distinct terminal state, not a success.

This taxonomy — wrong-term, wrong-name, missing-instance, incomplete, no-progress, silently-admitted — is a first pass at exactly the category system the project’s core statistical question depends on (docs/resources.md §5–6). It should be revisited and refined once real agent transcripts exist to check it against.

14 From tactics to the agent pipeline

Everything above described tactics as something you type in VS Code, watching the Infoview update live. The agent harness replaces that human loop with a programmatic one: the agent receives a serialized goal state (context + goal, roughly what’s printed above the ⊢ in every example in this document), proposes one tactic string, and receives back either the next goal state or one of the error categories from §13 — with no Infoview, no hover tooltips, no exact? search run interactively (though the agent can still issue exact? as a tactic and read its output).

Concretely, this means the command-line invocation from the Lean 4 Environment Setup chapter, §8 (lake env lean file.lean, or the Lean REPL / language server protocol) is the actual interface the agent talks to — not VS Code. Every tactic in this tutorial is a string the agent must produce syntactically correctly before Lean even attempts to check whether it’s semantically valid, which means malformed syntax (missing import, wrong bracket type, a Mathlib-only tactic invoked without the import) is itself a distinct failure mode, prior to and separate from a mathematically wrong tactic.

The next documents in this project build directly on this:

  • The Agent\(\leftrightarrow \)Lean 4 Pipeline chapter (Goal 6) — the exact protocol between agent and Lean, and how goal states get serialized/parsed.

  • The agent-thinking logging design (Goal 8) — what gets recorded at each of these steps, building on the error taxonomy in §13.

  • The problem set (Goal 9) — segmented using exactly the topic split in §10–12 (set theory / topology / algebra), difficulty-tiered partly along the “generic tactics suffice” vs. “requires exact lemma recall” axis observed in §12.

15 Mathlib conventions: naming, dot notation, anonymous constructors

Section 13 flagged “wrong lemma name” as a major hallucination category once problems require real Mathlib recall (topology and deeper algebra especially). It’s worth knowing that Mathlib names are not arbitrary — they follow a documented, learnable scheme. Internalizing it (for you and, eventually, as prior knowledge encoded into the agent’s prompting) turns “guess the name” into “derive the name.”

15.1 Capitalization signals the kind of thing

  1. Proofs and theorem names (terms of a Prop) use snake_case: add_comm, mul_zero, lt_of_le_of_ne.

  2. Types, structures, classes use UpperCamelCase: Group, TopologicalSpace, Subgroup.

  3. Everything else (functions, other data) uses lowerCamelCase.

So seeing Nat.add_comm (snake_case after the dot) tells you it’s a proof; seeing TopologicalSpace (UpperCamelCase) tells you it’s a class before you’ve read anything else about it.

Knowing this, a name like mul_left_cancel is readable on sight: “multiplication, left [argument], cancel[lation].” not_le_of_gt reads as “not (≤), given (>)” — matching its actual statement a < b → ¬ b ≤ a. This is exactly the skill that turns exact?/#loogle from a crutch into a check.

15.3 Hypothesis ordering: “of”

When a name encodes hypotheses, they’re listed via _of_ in the order they appear in the statement, not reversed: a theorem A → B → C is named C_of_A_of_B. lt_of_le_of_ne therefore states something like a ≤ b → a ≠ b → a < b — conclusion first, then each hypothesis in argument order.

15.4 ≤ / < vs ≥ / >

Mathlib almost always states things with ≤ / <, never ≥ / >, but still uses ge/gt in names in a few specific situations: when two occurrences of the same relation in one name need to be told apart (le/lt for the first, ge/gt for a swapped second), when matching another relation’s argument order, or when describing an argument-swapped version. If you’re hunting for a lemma and _le_ isn’t found, try _ge_ before giving up.

15.5 Dot notation and the anonymous constructor

h.left, h.mp, f.comp g — a leading dot after a term calls a function in that term’s namespace with the term as first explicit argument of matching type. And.left : P ∧ Q → P becomes h.left when h : P ∧ Q. This is why Continuous.comp, seen in §11, can be written hg.comp hf.

The anonymous constructor ⟨...⟩ builds a term of a structure/inductive type by position, letting Lean infer which constructor from the expected type — this is what’s happening every time you write ⟨n, hn⟩ to prove an ∃, or ⟨hp, hq⟩ to prove a ∧.

15.6 Structural suffixes worth recognizing

  • .ext — a lemma of shape (∀ x, f x = g x) → f = g; the thing ext (§8) invokes.

  • .ext_iff — the bidirectional version, f = g ↔ ∀ x, f x = g x.

  • .inj / _injective / _inj — injectivity; .inj is usually a unidirectional, auto-generated constructor fact, _inj a bidirectional iff, _injective a full Function.Injective f statement.

  • Is-prefixed classes (IsOpen, IsClosed, IsTopologicalRing) — a Prop-valued class describing an extra property of data you already have, as opposed to extra data itself.

Full reference (symbol dictionary, capitalization rules, structural-lemma conventions, more examples): Mathlib naming conventions, cataloged in docs/resources.md.

16 Exercises (with worked solutions)

Work these before moving to the pipeline docs — they exercise every tactic family from §2–9 and preview the topic split from §10–12. Solutions follow each prompt; cover them and attempt the proof first.

1. Core tactics. Prove (P Q : Prop) (hpq : P → Q) (hp : P) : Q. 

example (P Q : Prop) (hpq : P → Q) (hp : P) : Q := by
  exact hpq hp

2. Rewriting. Prove (a b c : Nat) (h1 : a = b) (h2 : b = c) : a + 1 = c + 1. 

example (a b c : Nat) (h1 : a = b) (h2 : b = c) : a + 1 = c + 1 := by
  rw [h1, h2]

3. have/suffices. Prove (n : Nat) (h : n > 10) : n > 0 two ways: with have, then with suffices. 

example (n : Nat) (h : n > 10) : n > 0 := by
  have h' : n > 10 := h
  omega

example (n : Nat) (h : n > 10) : n > 0 := by
  suffices h' : n > 10 by omega
  exact h

4. Induction. Prove (n : Nat) : n < n + 1 by induction (don’t just reach for omega — practice using ih). 

example (n : Nat) : n < n + 1 := by
  induction n with
  | zero => omega
  | succ m ih => omega   -- ih available but omega doesn't need it here;
                          -- compare with a genuinely inductive fact like §5's add_zero'

(Note: this particular fact is linear and omega alone would close the top-level goal without induction — the exercise is in the induction mechanics: naming ih, understanding it’s unused here because the fact doesn’t recurse on n’s structure. Try theorem double_ge (n : Nat) : n ≤ 2 * n by induction for a case where ih is genuinely load-bearing.)

5. Case split + automation. Prove (n : Nat) : n % 2 = 0 ∨ n % 2 = 1. 

example (n : Nat) : n % 2 = 0 ∨ n % 2 = 1 := by omega

6. ring vs omega. Prove (x y : Int) : (x + y) * (x + y) = x*x + 2*x*y + y*y, and separately (a b : Nat) (h : a ≤ b) : a + 3 ≤ b + 3. Identify which tactic fits which. 

example (x y : Int) : (x + y) * (x + y) = x*x + 2*x*y + y*y := by ring
example (a b : Nat) (h : a ≤ b) : a + 3 ≤ b + 3 := by omega

7. by_contra. Prove (n : Nat) (h : ¬ n = 0) : n > 0. 

example (n : Nat) (h : ¬ n = 0) : n > 0 := by
  by_contra hc
  push_neg at hc
  omega

8. calc. Prove (a b c : Nat) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c with an explicit calc chain (not just exact le_trans h1 h2). 

example (a b c : Nat) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c := calc
  a ≤ b := h1
  _ ≤ c := h2

9. rcases/obtain. Prove (h : ∃ n : Nat, n > 3 ∧ n < 6) : ∃ n : Nat, n > 0. 

example (h : ∃ n : Nat, n > 3 ∧ n < 6) : ∃ n : Nat, n > 0 := by
  obtain ⟨n, hn1, hn2⟩ := h
  exact ⟨n, by omega⟩

10. Set theory. Prove (A B C : Set α) : A ∩ (B ∪ C) = (A ∩ B) ∪ (A ∩ C) — you saw this in §10; write it here from a blank slate. 

example (A B C : Set α) : A ∩ (B ∪ C) = (A ∩ B) ∪ (A ∩ C) := by
  ext x
  simp only [Set.mem_inter_iff, Set.mem_union]
  tauto

11. Set theory, subset chain. Prove (A B C D : Set α) (h1 : A ⊆ B) (h2 : B ⊆ C) (h3 : C ⊆ D) : A ⊆ D. 

example (A B C D : Set α) (h1 : A ⊆ B) (h2 : B ⊆ C) (h3 : C ⊆ D) : A ⊆ D := by
  intro x hx
  exact h3 (h2 (h1 hx))

12. Algebra. Prove {G : Type*} [Group G] (a b c : G) (h : a * b = a * c) : b = c (left cancellation) using mul_left_cancel or by hand via mul_left_cancel₀-style reasoning — try exact? first if the exact name isn’t obvious. 

example {G : Type*} [Group G] (a b c : G) (h : a * b = a * c) : b = c := by
  exact mul_left_cancel h

13. Combinators. Prove (b1 b2 : Bool) : (b1 && b2) = (b2 && b1) by casing on both booleans and closing every resulting goal with one combinator call. 

example (b1 b2 : Bool) : (b1 && b2) = (b2 && b1) := by
  cases b1 <;> cases b2 <;> rfl

14. Diagnose the error. The following proof fails. Without running it, predict which error category from §13 it hits, then fix it. 

example (n : Nat) : n + 0 = n := by
  exact Nat.add_zer n   -- typo: should be Nat.add_zero

Diagnosis: unknown identifier — Nat.add_zer doesn’t exist (missing final o). This is exactly the “plausible-sounding but nonexistent name” hallucination flagged in §13; the fix is either correcting the typo or reaching for exact?.

15. Cross-topic capstone. Prove that for a continuous function f : ℝ → ℝ and a set S that’s the preimage of an open set under f, S is open — i.e., restate and prove Continuous f → IsOpen U → IsOpen (f ⁻¹’ U) using the definitional unfolding from §11. 

example (f : ℝ → ℝ) (hf : Continuous f) (U : Set ℝ) (hU : IsOpen U) :
    IsOpen (f ⁻¹' U) := by
  exact hf.isOpen_preimage U hU

(If the exact lemma name here doesn’t resolve in your environment, this is a live example of the topology-specific “lemma recall” difficulty flagged in §12 — use exact? and cross-check against Mathlib.Topology.Continuous in docs/resources.md.)
