5 Agent and Lean 4 Pipeline

Agentic Hallucinations — Independent Study. Design spec for how the agent and Lean 4 actually communicate, and what “environment switching” means across this project’s full stack. Written to be concrete enough to hand to an implementer (human or Claude Code) as a blueprint — not just a description.

Sources: leanprover-community/repl (protocol fetched and quoted directly below), Pantograph (arXiv:2410.16429), lean-lsp-mcp, LeanInteract. Full bibliography: docs/resources.md.

1 The loop, restated precisely

From the original project brief: the agent is given a theorem, proposes one tactic, Lean verifies it, and either returns a new goal state or an error — repeat until the goal list is empty (proved) or some stopping condition is hit (budget exhausted, agent gives up, non-termination).

Stated as a state machine: 

state = (theorem, goal_stack, history)
loop:
  agent.observe(goal_stack, history) → tactic_string
  result = lean.apply(tactic_string, goal_stack)
  if result.ok and result.goals == []:
      state = PROVED; stop
  elif result.ok:
      goal_stack = result.goals
      history.append((tactic_string, "success", result.goals))
  else:
      history.append((tactic_string, "error", result.error_message))
      # goal_stack unchanged — agent tries again from the same state,
      # now with the error message added to what it can see
  if budget_exhausted or agent_signals_stop:
      state = FAILED; stop

Everything in this document is about making lean.apply(...) a real, callable thing, and about what goal_stack and result actually look like on the wire — because that representation is what determines what the agent can see, and therefore what “hallucination” even means operationally (proposing a tactic that’s invalid given what it could see, vs. one that’s invalid period).

2 Candidate interfaces, surveyed

There is no single official “Lean API for agents” — four real options exist, each with different tradeoffs:

Interface

How it works

Strengths

Weaknesses

File + lake env lean (from the Environment Setup chapter, §8)

Write a whole .lean file, run lake env lean file.lean, parse stdout/stderr

Zero extra dependencies; exactly what CI and the setup doc already verify

No incremental state — every attempt re-elaborates the whole file from scratch; painfully slow for a multi-step tactic loop; output is meant for humans, not machines

leanprover-community/repl

Persistent process, JSON in/out over stdin/stdout, proofState integers track state incrementally

Purpose-built for exactly this; incremental (no re-elaboration per tactic); structured JSON; supports backtracking via reusing an earlier proofState/env id

“Experimental” tactic mode per its own README; one Lean process = one project’s environment, so multi-project setups need multiple processes (see §5)

Lean language server (LSP), via lake serve or wrapped as lean-lsp-mcp

The same server VS Code talks to; JSON-RPC 2.0; query goal state at a file position

Reuses infrastructure that’s already battle-tested by every human Lean user; also exposes hover/definition/diagnostics beyond just tactic state

Designed around a live-edited file, not a clean append-only tactic stream — mapping “propose one tactic” onto “edit this file at this position” is more indirect than the REPL’s native {"tactic": ..., "proofState": ...} shape

Pantograph

Purpose-built ML-facing API/REPL, supports tree search (MCTS) natively

Most feature-rich for search-heavy agent designs; used in published LLM+Lean pipelines (Draft-Sketch-Prove)

Heavier dependency, smaller community than the REPL above; overkill if the agent is doing simple sequential tactic proposal rather than tree search

Recommendation for this project: the leanprover-community/repl, wrapped in Python (directly, or via LeanInteract). It matches the project’s stated loop shape almost exactly (see the tactic-mode example below), is incremental (fast — no re-elaborating the whole file per tactic), and is simple enough to reason about and log precisely, which matters more here than raw proof-search power. Revisit Pantograph if/when the harness grows a tree-search or backtracking-heavy agent design rather than the linear one-tactic-at-a-time loop described in the project brief.

3 The REPL protocol, concretely

Run via lake exe repl (or, pointed at a specific project’s dependencies: lake env /path/to/repl/.lake/build/bin/repl). Communicates via one JSON object per command, blank-line separated, on stdin, with one JSON object back on stdout.

3.1 Starting a theorem (command mode to tactic mode)

You open tactic mode by sending a command containing a sorry; the response gives you a proofState id to start from: 

// → stdin
{"cmd": "theorem my_thm (x : Unit) : Nat := by sorry"}

// ← stdout
{"sorries":
 [{"proofState": 0,
   "pos": {"line": 1, "column": 29},
   "goal": "x : Unit\n⊢ Nat",
   "endPos": {"line": 1, "column": 34}}],
 "messages":
 [{"severity": "warning", "pos": {...}, "endPos": {...},
   "data": "declaration uses 'sorry'"}],
 "env": 0}

goal here — "x : Unit\n⊢ Nat" — is exactly the goal-state text this project’s tutorial (the Lean 4 Tutorial chapter, §1) teaches how to read. This is the string (or a structured equivalent) the agent should be shown at each step.

3.2 One tactic step

// → stdin
{"tactic": "apply Int.natAbs", "proofState": 0}

// ← stdout
{"proofState": 1, "goals": ["x : Unit\n⊢ Int"]}

// → stdin
{"tactic": "exact -37", "proofState": 1}

// ← stdout
{"proofState": 2, "goals": []}

"goals": [] is the terminal success state — the theorem is proved. This is the exact shape of lean.apply() from §1: input is {tactic, proofState}, output is a new proofState plus the resulting goals list (empty on success).

3.3 The error case

An invalid tactic doesn’t crash the process — it returns a messages array with "severity": "error" and the proof state does not advance (you’re still at the same proofState, free to try again): 

// → stdin
{"tactic": "exact 37", "proofState": 1}   // wrong: goal wants Int, not the literal misapplied here

// ← stdout (schematic — exact message text depends on the specific mismatch)
{"proofState": 1,
 "messages": [{"severity": "error", "data": "type mismatch ..."}]}

This is the critical mechanic for the hallucination analysis: a rejected tactic does not lose progress — the agent is still at proofState 1 and can retry. So “how many iterations to converge” (from the project’s core question) is naturally just the count of tactic-submission round-trips, separable into accepted-and-advanced vs. rejected-and-retried, per proofState.

3.4 Backtracking and persistence

Any earlier env or proofState integer can be reused as the starting point for a new command — this is backtracking, for free, without re-running anything. States can also be pickled to .olean files and restored later ({"pickleTo": "path", "proofState": n} / {"unpickleProofStateFrom": "path"}), which matters for §6 (long-running logging) and for resuming an interrupted batch run.

5 Environment switching — three distinct senses

“Environment switching” turns out to mean three different things at three different layers. Conflating them is an easy source of bugs once the harness is running many theorems across topics.

5.1 Toolchain/project switching

Each Lean project pins a lean-toolchain (exact compiler version) and a lakefile dependency set (which Mathlib commit, which other libraries). A single REPL process is started via lake env <repl-binary> inside a specific project directory and inherits that project’s toolchain and imports for its whole lifetime.

For this project’s problem set (set theory / topology / algebra, all drawn from Mathlib per the Lean 4 Tutorial chapter, §10–12), one Mathlib-linked project should suffice for all three topics — Mathlib is a single library spanning all of them, so topic segmentation is a content/selection concern, not an environment concern. Toolchain switching only becomes real if the problem set later pulls in an external benchmark repo with its own pinned toolchain (e.g. cloning miniF2F or PutnamBench directly rather than re-stating their theorems inside our own project — see docs/resources.md §3). In that case, the harness needs one REPL process (and one working directory) per distinct toolchain, and a router that dispatches each theorem attempt to the correct process based on which benchmark it came from.

5.2 Session/state switching

Within a single REPL process, each theorem attempt starts from a fresh env/proofState (§3). Retrying a theorem, or exploring two different tactic choices from the same point, is just reusing an earlier proofState id rather than starting over — cheap, and exactly what makes backtracking-capable agent designs (or simply “let me log both the accepted path and the road not taken”) tractable. The harness needs a clear policy here: does a new attempt at the same theorem get a fresh proofState 0, or does it resume from wherever the last attempt got stuck? (Recommendation: fresh state per attempt, logged as a new attempt_id — resuming from a stuck point conflates “the agent tried again” with “the agent kept going,” which are different statistical events.)

5.3 Interface switching (human vs. machine)

This is the sense closest to the original phrasing of Goal 7 (the not-yet-written fluency guide) and to the Environment Setup chapter, §8: VS Code + the Lean 4 extension is how you build, debug, and sanity-check problems interactively (Infoview, hover, exact? suggestions rendered inline); the REPL (or LSP-via-MCP) is how the harness talks to Lean headlessly, with no human in the loop. A theorem should generally be authored and manually verified once in VS Code (confirm it’s actually provable, get a feel for its difficulty) before it’s added to the problem set the harness runs against — the REPL is not a good place to discover whether a theorem statement itself is even correct, only to run an already-trusted theorem through repeated automated attempts.

6 Failure modes at the plumbing level

Distinct from the mathematical error taxonomy in the Lean 4 Tutorial chapter, §13 (wrong term, wrong lemma name, missing instance, incomplete, no-progress, silent sorry), the harness also needs to handle failures in the plumbing itself — these are infrastructure bugs, not agent hallucinations, and conflating the two categories would corrupt the statistical analysis:

  • Malformed JSON / protocol violation — the agent (or a bug in the harness) sends something the REPL can’t parse. Should be caught and logged as a harness error, never attributed to the agent’s mathematical reasoning.

  • Process crash — the REPL process dies mid-session (e.g. Mathlib bug, memory exhaustion). Needs a restart-and-resume policy; whatever attempt was in flight should be marked incomplete_infra_failure, not failed.

  • Non-terminating tactic — some tactics (simp with a bad lemma set, certain aesop configurations) can hang rather than error. The harness needs a per-tactic timeout with a hard kill, and that timeout event is itself a data point worth logging (which tactics the agent proposes that are prone to hanging is exactly the kind of pattern the hallucination analysis wants to catch).

  • Resource exhaustion across a long run — REPL processes accumulate Environment/proofState objects in memory; a long batch run needs periodic process restarts (using the pickling mechanism from §3 to preserve any state worth keeping) rather than one REPL process for the entire experiment.

7 Open design decisions

Flagging these explicitly rather than silently deciding them — they affect the statistics, so they’re worth deciding deliberately once the logging doc (Goal 8) and problem set (Goal 9) exist alongside this one:

  1. What counts as “one iteration”? A single {"tactic": ...} call, or a semicolon/<;>-chained combinator treated as one agent turn (per the Lean 4 Tutorial chapter, §9’s note on this same ambiguity)? Affects every downstream “iterations to converge” statistic.

  2. Retry budget policy. Fixed max tactics per theorem? Max wall-clock time? Does the agent get to see the full history of its own rejected attempts, or only the current goal state?

  3. What exactly gets shown to the agent on error — the raw Lean error string (verbose, sometimes includes internal term representations) or a cleaned/truncated version? This is a real methodological choice: a cleaner error message could materially change the agent’s hallucination rate, which means it needs to be fixed and reported, not tuned ad hoc per run.

  4. Attempt independence. Are repeated attempts at the same theorem statistically independent draws (fresh proofState 0, no memory of prior attempts) or is the agent allowed to see its own history across attempts? Both are defensible, but they answer different questions, and the analysis needs to know which one was run.
